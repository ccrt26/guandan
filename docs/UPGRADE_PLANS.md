## 方案 1：教练报告持久化（关浏览器不丢）

### 目标
生成的教练报告从"标签页级"（sessionStorage，关标签即失）升级为"本机持久"（localStorage），删除对局时联动清理，并防存储配额溢出。

### 现状与依据（代码事实）
- 写入：`ReviewPage.tsx:393` `sessionStorage.setItem('gd_report_v2_' + record.id, full)`，仅生成完成时写一次（无增量写）。
- 读取：`ReviewPage.tsx:310` 挂载时读一次。
- 对局记录本身在 localStorage（`gd_record_{id}`，上限 40 局，saveRecord 落盘），因此**报告与对局的生命周期本应对齐，现在没对齐**。
- **已确认的泄漏**：`storage.ts deleteRecord()` 只删记录与索引，不删关联报告；记录裁剪（INDEX_LIMIT=40）时报告同样残留。
- 容量测算：单份报告实测 1.0~1.7KB（1200~1700 字）；40 局全部保留 ≈ 70KB；对局记录 40×20KB ≈ 800KB；两者合计 < 1MB，远低于 localStorage 常见 5MB 配额。**容量不是风险，泄漏与配额兜底才是。**

### 设计
1. **读写切换到 localStorage**，键不变（`gd_report_v2_{id}`，键内含数据版本，格式变更时换键即可作废旧报告——该机制已存在）。
2. **生命周期联动**（新增 `storage.ts` 两个函数，UI 只调用不实现）：
   - `deleteRecord(id)` 内加 `localStorage.removeItem('gd_report_v2_' + id)`；
   - `saveRecord` 裁剪掉第 40 名以外的旧记录时，同步删除其报告；
   - 新增 `pruneOrphanReports()`：启动时清理"记录已不存在"的报告（一次性自愈，兜住历史残留与手动清 localStorage 的半删状态）。
3. **配额兜底**：写入包一层 `safeSetItem`——捕获 QuotaExceededError，按报告时间戳从旧到新逐个删除并重试一次；再失败则静默放弃持久化（报告仍在内存中显示，本次会话不受影响），console.warn 留痕。
4. **离线报告一并持久化**：`buildOfflineReport` 分支（ReviewPage.tsx:397）现在不落任何存储。切 localStorage 后同样落盘，但正文前加哨兵标记 `<!--offline-->`；读取时检测哨兵则显示"离线版"横幅（现状该横幅由未持久化的 status 驱动，重进页面会丢，顺带修复）。
5. **pruneOrphanReports 执行点**：App 根组件 useEffect 挂载时跑一次（模块级旗标防 HMR 重复执行），不在各视图重复跑；全程 try/catch，失败不影响启动。
6. **读写策略**：只读写 localStorage（不回落 sessionStorage）。升级瞬间的旧标签页仍写 sessionStorage，其内容随标签关闭自然消失——一次性损失，可接受；新标签永远以 localStorage 为准，无双读歧义。
7. **多标签并发**：两个标签对同一键后写覆盖前写，内容均为该局合法报告，无损坏风险（setItem 整串写）；不做跨标签锁。
8. **版本键策略（强制）**：`gd_report_v2_` 中的版本号是唯一作废旧报告的机制——**任何影响报告内容口径的变更（归因逻辑、剧本格式、建议算法）必须 bump 为 v3**，否则持久化会把旧口径报告长期固定下来。
9. **不做的事**：不把报告并进 GameRecord 大 JSON（避免记录读写路径复杂化）；不做跨设备同步（那是未来存储层的课题，见 ARCHITECTURE 已知权衡）。

### 边界与异常
- 用户手动清浏览器数据：报告与记录一起没，行为符合直觉。
- 同一局重复生成：覆盖写，天然幂等。
- 隐私口径不变：报告内容不含 Key，Key 仍只在 gd_llm_config（现状如此）。

### 验证
- 手动：生成报告→关闭标签→重开复盘页，报告直接可见；删除对局→报告同步消失。
- 自动：`pruneOrphanReports`/`safeSetItem` 为纯逻辑（可提为不依赖 DOM 的函数，用现有 vitest 在 web 包新增一个测试文件；vitest 已在用，零新依赖）。
- 回归：现有 90 测试不受影响（改动只在 web 包）。

### 风险与回滚
- 风险低（新增代码 < 60 行，全部在 storage.ts 与 ReviewPage 两处读写点）。
- 回滚：恢复两处 sessionStorage 调用即可，键未变。

### 工作量
约 1 小时（含测试与浏览器验证）。

## 方案 2：界面层自动检测（防"按钮没反应"类问题）

### 目标
让界面回归（设置弹窗、切页丢报告、按钮无响应、拦截页）至少被一层自动或半自动流程覆盖，不再完全依赖用户手点发现。

### 现状与依据（代码事实）
- 现有 90 个测试全部是**逻辑层**（engine/review/ai）；web 包 0 测试。昨晚三起界面问题（设置弹窗不弹、切页丢报告、Playwright 点击无反应）全部靠人工发现。
- 未安装任何 DOM 测试设施（root devDependencies 无 jsdom/happy-dom/testing-library/playwright）。
- 用户红线：**未经允许不安装任何东西**。npm devDependency 虽只落在本项目 node_modules、不碰系统，但按红线同样需要明确批准。

### 设计（三档可选，建议按 2a→2b 顺序推进）

**2a. 零依赖：冒烟清单 + 自动陪跑开关（先做，立刻可用）**
1. 新增开发期功能 `?autopilot=1` URL 参数（`import.meta.env.DEV` 门控，生产构建不含）：让 AI 接管人类座位自动打完整局。已知**四个接入点**（审查确认，缺一不可）：
   - `scheduleNext()` 首行 `if (… || this.humanTurn) return`（controller.ts:197）对 0 号座位早退，autopilot 时须放行；
   - `players` Map 只装 1/2/3 号座位（controller.ts:72、204），需给 0 号注册 AI 实例（同一 difficulty，独立种子）；
   - TablePage 键盘空格/P 与出牌按钮直连 `humanPlay`（TablePage.tsx:103-112、234-238），autopilot 时必须禁用人类输入，防止与代打竞争出牌；
   - 结算后是模态框+人工点"复盘本局"（TablePage.tsx:180-181），冒烟步骤保留这一次人工点击（不自动路由，避免动 App 层）。
   公平性说明：代打 AI 与三个对手走完全相同的决策通路（只用自己手牌+公开信息，fairness 测试覆盖），不构成作弊；开启时桌面显示"🤖 自动驾驶（测试模式）"角标，与首页公平保证文案不冲突。
   这是后续任何界面检测的**基础设施**——不用人工打完一百多手就能测"对局→结算→记录→复盘"全链路。
2. `docs/SMOKE.md`：10 步冒烟清单（开新局/autopilot 打完/结算进入复盘/时间轴逐手/教练报告生成（离线模式）/切 tab 不丢/设置弹窗四视图可开/删除对局联动报告/损坏记录拦截页/历史统计），每步写明"期望看到什么"。
3. dev 模式加"页面错误显性化"：window error/unhandledrejection 钩子把错误钉在页面角落（Vite 只覆盖编译错误，运行时不明显）。
- 性质：**半自动**（我或用户按清单跑，autopilot 把最耗时的打牌环节自动化），零依赖零风险。

**2b. 组件级自动测试（需批准：新增 devDependency happy-dom + @testing-library/react，均为项目内依赖）**
- 覆盖对象（昨晚事故清单优先）：App 四视图路由与设置弹窗注入、ReviewPage 双 tab 用 CSS 隐藏不卸载（断言生成状态跨 tab 保留）、报告空正文错误分支、HistoryPage 删除联动、损坏记录渲染拦截页。
- 运行：并入 `npm test`。两个硬性配置（审查确认，不做则测试根本不执行或污染现有测试）：
  - `vitest.config.ts` 的 include 从 `packages/*/tests/**/*.test.ts` 扩为同时含 `**/*.test.tsx`（现模式不匹配组件测试文件）；
  - 环境用**逐文件声明** `// @vitest-environment happy-dom`（或 environmentMatchGlobs 限定 web 包），禁止全局 environment——否则现有 6 个 node 环境测试文件全部被切到 DOM 环境；
  - Vite5/esbuild 对 .tsx 默认 JSX automatic 编译可用，根配置无需挂 react 插件（CSS 仅一处 import，stub 掉）。
- 用例边界：涉及报告生成（fetch 流式）的用例只测离线路径或 mock fetch，不做真实网络；时间轴 122 个节点在 happy-dom 下渲染毫秒级，无性能问题。
- 局限（如实告知）：无真实浏览器渲染，**测不了布局/重叠/美观**——那是 2c 或人工验收的领域。
- 依赖体量：happy-dom 约 3MB 纯 JS；@testing-library/react 约 1MB；不下载浏览器内核、不碰系统。

**2c. 真实浏览器端到端（Playwright，暂不建议）**
- 能测布局几何与真实交互，但要下载 ~150MB 浏览器内核 + 项目依赖；当前界面规模下性价比低。触发条件：2b 上线后仍出现"渲染层"问题（布局重叠、动画、跨浏览器）再议。

### 边界与异常
- autopilot 属开发后门：生产构建路径不含（`import.meta.env.DEV` 门控），不影响正常游玩与公平性（不触 AI 决策路径，只是人类座位改由同一套本地 AI 代打）。
- 2b 的组件测试不 mock 引擎/分析器（用真实小样本对局 fixture），避免"测试替身与真实行为脱节"的假绿。

### 验证
- 2a：跑一遍 SMOKE.md 全绿；autopilot 模式将 aiDelayMs 由默认 600ms 调至 100ms（一局约 155 个决策点，600ms 默认约 93 秒，100ms 约 20~30 秒）且落盘记录通过完整性铁律。
- 2b：新测试进 `npm test`；故意删掉 ReviewPage 的 CSS 隐藏改动 → 测试必须变红（先红后绿的自我验证）。

### 风险与回滚
- 2a 风险≈0；2b 风险=依赖审批问题与测试维护成本；回滚=删测试文件+移除 devDependency。
- 红线声明：**2b/2c 未获明确批准前不动**，方案先以 2a 落地。

### 工作量
2a 约 1.5 小时；2b 约 2 小时（只做 3~4 个昨晚真实出过事的用例：设置弹窗四视图、报告 tab 不卸载、损坏记录拦截页、删除联动；不追覆盖率）。

## 方案 3：MatchController 职责拆分（❌ 已撤回，2026-10-25）

**撤回理由（项目原则：这是小游戏，不做大平台式设计）**：controller 224 行、16 个方法，对单人维护的小游戏完全在"一屏看懂"的范围内。拆成 Scheduler/RecordingService/Presenter 四件套是多人团队协作的模式，在单人项目里只会带来"改一处跳四文件"的维护成本，收益为零。今晚原方案连"种子注入 + autopilot 前置 + 同种子逐手对照"的验收成本都算上，投入产出比为负。
**替代承诺**：controller 保持单类；唯一的硬约束已经在位——落盘记录必须通过完整性铁律（integrity 测试守护），这比结构拆分更直接地防住了昨晚那类事故。若未来训练阶段真的需要第二个对局循环消费者，届时它直接复用 engine+ai（scripts/selfplay.ts 模式），也不需要动 controller。
（原方案全文见 git 前一版本/本节末尾折叠，此处不再保留，避免误导后续实施。）

## 方案 4：比赛进度保存与"继续比赛"（2026-10-26 实施完成；口径经用户修订：**存档点只在每局打完**，进行中的一局不做居中保存，刷新即重发该局）

### 目标
刷新/关浏览器后能继续同一场比赛：级数、局数、进贡/还贡状态不丢；**进行中的一局也能原样恢复**（手牌、轮次、桌面全部还原，从断点继续打）。

### 现状与依据（代码事实）
- 比赛进度只存在 MatchController 内存（MatchState：levels/gameNo/rngState/lastResult/lastHead），刷新即清零，每次都从 2 vs 2 重开。
- 引擎侧恢复条件全部具备：`MatchState` 各字段均可 JSON 序列化；`startGame()` 已按 `lastResult` 自动驱动进贡还贡（game.ts:95）。
- **进行中一局的恢复有现成基础设施**：Recorder 每手都在记录（含初始手牌）；`replay/stateBefore` 能确定性重建任意时刻局面；`memoryBefore` 能重建记牌器——复用昨晚大修的回放铁律。

### 设计
1. **存储**：localStorage 单键 `gd_match_current` = { match快照(级数/局数/lastResult/rngState/ruleOpts/difficulty), game: 进行中的 GameRecord | null }。写时机＝每手出牌后 + 每局结束 + 比赛结束清除。约 20KB/次，写延迟无感。
2. **首页"继续比赛"卡片**：有存档时显示「继续比赛 · 我方 X 对方 Y · 第 N 局进行中（第 M 手）/ 局间」+〔继续〕〔放弃比赛〕；无存档显示现有"开始比赛"；开新比赛提示替换旧存档。
3. **恢复两条路径**：
   - **局间恢复**（简单）：按快照重建 MatchState → startGame()，进贡还贡自动发生；
   - **局中恢复**（复用回放）：buildInitialState + 逐手重演到断点 → 完整局面（手牌/轮次/中央桌面）；人类记牌器=memoryBefore；三个 AI=createAI 后逐手喂 observe 事件（信息源与实局完全一致，仍只用公开信息）；Recorder 支持"续写"（注入已发生的 moves，终局合并成完整记录）。
4. **校验与降级**：恢复时跑 checkRecordIntegrity（进行中记录同样适用）——通过则原样续打；失败降级"按当前级数重新发一局"；快照也坏则放弃存档回首页。绝不带着坏数据硬续。
5. **清理**：过 A 结束、点"放弃比赛"、开新比赛覆盖时清除。
6. **不做的（小游戏原则）**：不做多存档槽（只有当前一场）；不做跨设备；不保存 UI 瞬态（已选未出的牌恢复后需重选）。

### 边界与异常
- 战绩/历史不受影响：仍只记录打完的局。
- AI 重建后与连续对局的差异仅在随机噪声级（种子不同），fairness 测试继续覆盖。
- 断点停在"正选牌"：局面恢复到断点，选牌重选，无损失。

### 验证
- 自动：存档读写/清理/损坏降级进 web/tests（沿用 localStorage stub）。
- 冒烟：autopilot 打到第 30 手 → 刷新 → 继续 → 手牌/轮次/级数与刷新前一致 → 打完整局 → 完整性铁律通过；SMOKE.md 加一步。

### 风险与回滚
- 新代码约 150 行（controller 恢复入口 + storage + 首页卡片 + Recorder 续写），全本地可回滚，不动引擎与复盘。

### 工作量
约 2~3 小时，零新依赖。
